# 用分区表归档商品表的历史数据

<!-- content-workspace-job:81922105-87ff-45f1-a7b2-71ad202fde6a -->

## 问题场景

商品表积累了几亿行历史数据，DELETE 老数据要跑几个小时，还产生大量 WAL，删完之后磁盘空间也不释放。

## 实现步骤

按时间范围建分区，每个分区对应一个时间段。

```sql
CREATE TABLE products_202611 PARTITION OF products
FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

归档时把整个分区从主表摘下来，元数据操作，瞬间完成。

```sql
ALTER TABLE products DETACH PARTITION products_202601;
```

查分区列表确认挂载关系，摘除后主表查询自动跳过该段。

```sql
SELECT inhrelid::regclass
FROM pg_inherits WHERE inhparent = 'products'::regclass;
```

## 注意事项

分区键必须出现在查询条件里才能裁剪，否则照样扫全部分区；主表上的唯一索引必须包含分区键，这是常见的建表失败原因。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

在跨团队协作时，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。
