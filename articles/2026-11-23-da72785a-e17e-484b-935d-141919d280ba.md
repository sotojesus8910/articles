## 问题场景

每个用例都重新建一遍凭证表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO vouchers (id, value) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 450 // 10 + 2)])
    yield conn
```

把常用查询封装成小工具函数，测试函数里只保留业务断言。

```python
def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM vouchers").fetchone()[0]
    assert n == 450 // 10 + 1 and n > 0
```

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

结合团队现状，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

对稳定性要求高的场景，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。
