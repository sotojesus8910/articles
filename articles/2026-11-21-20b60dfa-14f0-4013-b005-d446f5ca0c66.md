# 运单表深分页查询改用延迟关联

<!-- content-workspace-job:20b60dfa-14f0-4013-b005-d446f5ca0c66 -->

## 问题场景

运单表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM shipments WHERE weight > 120 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM shipments a
JOIN (SELECT id FROM shipments WHERE weight > 120
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM shipments a
JOIN (SELECT id FROM shipments ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

针对这类偶发问题，尽量把决策依据写进变更说明，避免资源被长期占用。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

从排障效率看，要明确各项资源的释放时机，确保线上行为始终可控。

遇到复杂链路时，优先保证失败时能快速定位原因，以便快速定位瓶颈。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。
