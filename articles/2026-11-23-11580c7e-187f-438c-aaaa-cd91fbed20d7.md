## 问题场景

对赠品做分组聚合时，单进程跑满一个核，其余核空闲，整批处理时间被计算量卡住。

## 实现步骤

把数据按行区间切成若干块，每块交给一个子进程独立计算，避免共享内存竞争。

```python
def partial(args):
    path, start, end = args
    total = 0
    for line in read_slice(path, start, end):
        total += int(line.split(",")[-1])
    return total
```

子进程返回局部聚合结果，父进程只做加法合并，不在父子之间传原始数据。

```python
from multiprocessing import Pool

def scan(path, size):
    jobs = [(path, i, min(i + size, total_lines(path))) for i in range(0, total_lines(path), size)]
    with Pool(processes=4) as pool:
        return sum(pool.map(partial, jobs))
```

## 验证方法

用单进程结果作为基准，核对进程池输出的总量完全一致，再比较耗时。

## 注意事项

传给子进程的函数必须可序列化，闭包和 lambda 在 spawn 模式下会失败；Windows 上要放在 if __name__ 保护里。

从成本角度看，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

结合团队现状，可以通过日志补充上下文信息，使整体改动风险可控。

在资源受限的环境下，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，避免资源被长期占用。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

对稳定性要求高的场景，需要评估对现有调用方的影响面，确保线上行为始终可控。
