# 部门字典查询加上缓存后减少重复计算

<!-- content-workspace-job:69a99d77-1ba9-4076-83bc-bc54f3393602 -->

## 问题场景

每次渲染部门详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["headcount"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

监控缓存命中率，命中率长期偏低说明入参过于分散，缓存没有意义。

```python
a = summary("dept-1", 35)
b = summary("dept-1", 35)
print(a == b, summary.cache_info().hits)
```

## 验证方法

连续调用同一参数两次，第二次的耗时应显著低于第一次，且返回值完全一致。

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

上线初期，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

在资源受限的环境下，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

针对这类偶发问题，尽量把决策依据写进变更说明，避免资源被长期占用。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

如果数据量继续增长，优先用工具把现状量化出来再动手，让容量规划更有依据。
