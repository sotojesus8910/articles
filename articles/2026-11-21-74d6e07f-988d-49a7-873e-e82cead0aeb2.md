# 用 outbox 模式保证传感器事件不丢

<!-- content-workspace-job:74d6e07f-988d-49a7-873e-e82cead0aeb2 -->

## 问题场景

传感器下单后要发消息通知下游，代码里先写库再发 MQ。中间进程崩溃，库里有了订单但消息没发出去，下游永远收不到。

## 实现步骤

在业务表旁边建一张 outbox 表，与业务写入放在同一个事务里。

```sql
INSERT INTO outbox (id, topic, payload, status)
VALUES (?, ?, ?, 'new');
```

独立线程轮询未投递的记录，发送成功再标记，失败保留待重试。

```java
@Transactional
public void place(Sensor o) {
    repo.save(o);
    outbox.save(event(o));
}
```

多实例轮询时用 SKIP LOCKED 避免重复取同一条。

```sql
SELECT id, payload FROM outbox
WHERE status = 'new' ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;
```

## 注意事项

outbox 表会持续增长，要配定期清理；下游必须能处理重复消息，至少一次投递无法保证只发一次。

从长期维护角度看，先把最小可复现的用例固定下来，以便后续复盘有据可查。

在迁移过程中，可以通过日志补充上下文信息，保证每一步都可验证。

在跨团队协作时，要避免在高峰期执行这类操作，避免问题积累到难以收场。

上线初期，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

在压测阶段，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。
