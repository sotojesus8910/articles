## 问题场景

保单结算按当天日期算账期，测试在月初和月末跑出不同结果，偶尔在半夜失败一次。

## 实现步骤

业务代码统一从模块内的 now() 取时间，不在函数深处直接调 datetime.now。

```python
from datetime import datetime, timedelta

def now():
    return datetime.now()

def period(days=0):
    d = now() + timedelta(days=days)
```

测试用 monkeypatch 把 now 换成返回固定时间的函数，覆盖月末、闰年、跨年三个点。

```python
def test_month_end(monkeypatch):
    import billing
```

断言只比较账期字段，不比较格式化后的完整字符串，避免时区差异干扰。

```python
def test_year_end(monkeypatch):
    import billing
    monkeypatch.setattr(billing, "now", lambda: datetime(2025, 12, 31, 12, 0))
    assert billing.period(1) == "2026-01"
```

## 验证方法

在三个固定时间点各跑一次，账期结果应当分别落在预期月份。

## 注意事项

不要 patch 内建 datetime 类本身，影响面太大；monkeypatch 在用例结束时自动还原，手动改全局变量容易污染后续用例。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

结合团队现状，可以通过日志补充上下文信息，使运维成本保持在合理区间。

遇到复杂链路时，先把最小可复现的用例固定下来，以便后续复盘有据可查。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

在多人协作的项目里，应当拆分步骤以便中途校验，避免资源被长期占用。

在迁移过程中，可以通过压测确认容量水位，之后再考虑扩大适用范围。
